# Reference — Staging sheet

> **Status:** Reference. Describes an external system that Trueup does not control.

The **email extractor** is an existing program, independent of Trueup. Every day it reads the
owner's bank notification emails and writes one row per notification, verbatim and without
interpretation, to a spreadsheet: the **staging sheet**. Trueup reads the staging sheet. It never
writes to it and never changes the extractor (`docs/product.md`, 7.5).

The location of the staging sheet and the credentials to read it are configuration of the
owner's workspace. They are never part of this repository.

## Tabs

| Tab | Content |
|---|---|
| `Staging` | One row per notification. Headers on row 2; data from row 3 |
| `Import Log` | One row per extractor run. Headers on row 2; data from row 3 |
| `Config` | The extractor's own settings, as key–value rows |
| `README` | Notes for people |

## `Staging` columns

Columns are identified by position. The header text on row 2 describes them; confirm it during
the dependency test of the staging-sheet reader (`docs/backlog.md`, B-21).

| Column | Content |
|---|---|
| A | Row identifier generated by the extractor |
| B | Identifier of the email. Present on every row the extractor writes |
| C | Identifier of the email's thread |
| D | When the email was received, `yyyy-MM-dd HH:mm`, in the extractor's time zone |
| E | Sender address |
| F | Subject |
| G | Institution, as named by the extractor |
| H | Template: which notification layout produced the row |
| I | Operation identifier, stored as text so leading zeros survive. When a notification has none, the extractor builds a synthetic one from date, time, amount and counterparty, and says so in column AA |
| J | Operation date, `yyyy-MM-dd`. Can be empty |
| K | Operation time, `HH:mm`. Can be empty |
| L | Amount, as a number, without sign |
| M | Currency of L, as a symbol written by the extractor |
| N | A second amount, when the notification carries two |
| O | Currency of N |
| P | Source identifier: the account or card the money left |
| Q | Source label, as written in the notification |
| R | Destination identifier |
| S | Destination label, as written in the notification |
| T | Counterparty text — merchant, person or company — as written |
| U | Operation type, as written in the notification |
| V | Commission, when the notification reports one |
| W | Channel, when the notification reports one |
| X | Extra field 1. Its meaning depends on the template |
| Y | Extra field 2. Its meaning depends on the template |
| Z | Parse status: `ok`; `partial` — the amount was read but a required field is missing; `failed` — the amount is missing or the email could not be parsed |
| AA | Notes from the extractor, separated by `\|`: missing fields, synthetic identifiers, warnings |
| AB | Import status written by the extractor. A hint for people only, never a control |
| AC | Unused |
| AD | The email body as plain text, up to 4,000 characters, when the extractor is configured to keep it |

## What a row does and does not say

- A row never contains a sign, a category, an account mapping or a transfer pairing.
  Interpreting it is Trueup's job.
- Amounts carry no sign. Whether money left or arrived follows from the template and the
  identifiers.
- Text written by an institution can be wrong: for example, a transfer to a third party labelled
  as a transfer between the customer's own accounts. Only identifier mappings decide which
  accounts are involved (`docs/domain.md`, `ID-1`).
- Some templates do not carry every field, such as the operation date or the source account.
  Those rows have parse status `partial` or `failed`; the missing data becomes a review item and
  is never filled by assumption.
- Notifications the extractor classifies as noise — statements, security codes — never produce
  rows. Statements reach Trueup only when the owner uploads them.
- The extractor writes each operation identifier once, ignoring leading zeros, and each email
  once.

## Reading the sheet completely

1. Read the whole spreadsheet, every tab, as typed data: numbers as numbers, dates as dates, and
   identifiers as text with their leading zeros. Never use a reader that returns a summary or a
   natural-language rendering of the sheet: such readers can drop rows without reporting an
   error.
2. Count the `Staging` rows that have a value in column B, from row 3. Never use the sheet's last
   row: the sheet is formatted far below its data.
3. Add up the `New rows` column of `Import Log`, from row 3. The column is found by its header
   name on row 2.
4. The read is complete only when both numbers are equal and the counted rows are contiguous.
   Otherwise nothing from that read is processed, and the mismatch is reported.

## Keys

Trueup's external key for a row is its operation identifier (column I) with leading zeros
removed. When column I is empty, the key is the email identifier (column B), marked so that the
two kinds of key cannot collide (`docs/domain.md`, `CAP-2`).

## `Import Log` columns

| Column | Content |
|---|---|
| A | When the run happened |
| B | What started it: the daily schedule or a manual run |
| C | Emails examined |
| D | `New rows`: rows written to `Staging` |
| E | Emails skipped as already written |
| F | Emails skipped as noise |
| G | Rows written with parse status `failed` |
| H | Rows written with parse status `ok` |
| I | Rows written with parse status other than `ok` |
| J | Notes, such as a run stopped early |
